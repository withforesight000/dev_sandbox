# セキュリティモデル

[English version](security-model.md)

この文書では、Dev Container の境界によって制限することを意図している範囲、
AI エージェントから見えるもの、そして信頼する必要が残るデプロイ上の前提を
説明します。これはリポジトリの公開範囲を制御するための境界であり、microVM
や外向き通信を原則拒否するネットワークポリシーを完全に代替するものでは
ありません。

## セキュリティ目標

標準構成では、実用的な Dev Container と内部の rootless Docker デーモンを
維持しながら、関係のないホスト上のデータをエージェントのファイルシステム
から遠ざけることを目指します。Dev Containers クライアントは現在のリポジトリ
を `workspace` サービスへマウントします。追加リポジトリは、コンテナ側の
マウント先とともに `.devcontainer/allowlist.tsv` で選択します。`@workspace` の
行を使えば、現在のリポジトリも `docker` サービスを含む生成マウントへ追加
できます。

内部デーモンを使うのは、リポジトリで Docker や Compose を利用しながら、
エージェントに外側の Docker デーモンを制御させないためです。rootless で非特権
ユーザー `dev` として動かすことで、内部のワークロードが侵害された場合に、
デーモンとそのコンテナが持つ権限を抑えます。外側の Docker socket は意図的に
マウントしません。これを公開するとエージェントが外側のデーモンを制御でき、
リポジトリ単位の境界が損なわれるためです。workspace は専用の `docker` サービス
が提供する socket を使います。

リポジトリのコンテナ内のマウント先を変えても、コンテナ内での見え方が整理
されるだけです。そのリポジトリのファイルに対してエージェントが持つアクセス
範囲が狭くなるわけではありません。設定した宛先がそのまま canonical なパスに
なり、移動用 alias は生成されません。`/workspaces` 配下のネストした宛先に対する
合成された親ディレクトリは一時的な `tmpfs` であり、ホスト側の親ディレクトリ全体
を公開するものではありません。

ホスト側の準備処理は allowlist を解決し、選択されたホスト側 source path を含む
Compose 設定を生成します。そのため、リポジトリ内のテスト・検証スクリプト
（`tests/validate.sh` など）では、`repo-alpha` や `repo-beta` のような中立的な名前の
一時リポジトリを使ってください。ユーザー固有の allowlist に対して本番用の準備処理を
実行したり、その処理が生成した出力を公開したりしてはいけません。

Dev Containers クライアントは、Dev Container の起動前に `initializeCommand` を通じて
`prepare-mounts` をホスト上で実行します。準備処理のコードと allowlist の変更は
ホストに影響し得るものとして扱い、Dev Container を再開する前にレビューしてください。
パスの検証だけでは、その変更がレビュー担当者に承認されたものかどうかは確認できません。

## 保護するもの

`.devcontainer/allowlist.tsv` に記載された追加リポジトリのパスは、各行で指定
されたコンテナ側の宛先にマウントされます。通常の構成では、次のものをマウント
しません。

- ホストのホームディレクトリ
- SSH 鍵ファイルやクラウド認証情報
- ホストの Docker 設定ファイルや外側の Docker socket
- 複数のリポジトリを含む任意の親ディレクトリ

allowlist は Compose の起動前に検証されます。存在しないパス、リポジトリでない
パス、入れ子になったパス、重複するエントリ、重複または入れ子になったコンテナ
側の宛先、サービスが所有する固定マウント自身またはその親・配下となる宛先、
不正な行、不正な宛先は、fail-closed で拒否されます。この固定マウント検証の対象は
`/docker-socket`、`/tmp`、`/home/dev/.cache/mise`、
`/home/dev/.local/share/mise`、`/home/dev/.local/share/docker`、
`/home/dev/.codex`、`/home/dev/.claude`、`/run/ssh-agent` です。検証は生成した
Compose 出力を書き込む前に完了するため、衝突した宛先が Compose の起動まで到達する
ことはありません。追加リポジトリは Git リポジトリのルートである必要があり、各行には
コンテナ側の絶対パスを指定する必要があります。`@workspace` で参照される現在の
リポジトリは、追加リポジトリに対する Git ルート検証の対象外となる意図的な例外です。
`/workspaces` 自体だけが予約されるため、その配下の宛先は引き続き使用できます。

## 保護しないもの

allowlist に登録したすべてのリポジトリは、エージェントの信頼境界内にあります。
エージェントは、隠しファイル、Git hook、ビルドスクリプト、ローカル設定を含む
その中のすべてを読み取り、書き込み、削除、実行できます。リストは最小限に
保ち、エージェントに扱わせたくない機密情報を含むリポジトリは登録しないで
ください。

エージェントは内部の rootless Docker デーモンを操作でき、その Dev Container
から見えるパスをマウントするコンテナを作成できます。rootless Docker はより
強い境界を提供しますが、絶対的なセキュリティ保証ではありません。カーネルの
脆弱性、特権設定の誤り、新たに追加されたホストマウントによって境界が弱く
なる可能性があります。

allowlist はネットワークアクセス、allowlist 内のリポジトリで動作するプロセス
の挙動、内部デーモンが作成したコンテナの内容を制限しません。macOS の Docker
Desktop では、現在のリポジトリと実際に使う追加リポジトリだけを File Sharing
の対象にしてください。広いホームディレクトリの親を共有すると、ホスト側で
意図した境界が損なわれます。

## 信頼上の前提

### 外側のコンテナランタイム

Docker デーモンコンテナは、RootlessKit が namespace を設定するために必要とする
範囲で、外側のコンテナランタイムでは `privileged` として実行されます。デーモン
プロセスは非特権ユーザー `dev` で動作し、デーモンが作成するコンテナも rootless
の user namespace を通じてホストの root 権限を持たずに動作します。外側の Docker
socket は `workspace` と `docker` のどちらのサービスにもマウントされず、デーモン
コンテナに渡されるのは明示的に allowlist に登録したリポジトリのパスだけです。
データルートと Unix socket は名前付きボリュームに分離されています。

外側の `privileged` と `seccomp:unconfined` の設定は、RootlessKit と内部デーモンを
動作させるためのものです。rootless が適用されるのは内部デーモンとそのワークロード
であり、外側のサービスではありません。そのため、外側のランタイムとホストカーネルは
引き続き信頼境界の一部です。

外側のコンテナランタイム、ホストカーネル、特権付きの `docker` サービス、Dev
Container イメージ、追加のホストマウントは、デプロイにおける信頼上の前提として
残ります。イメージと Docker Desktop または Linux ホストを最新の状態に保って
ください。

### 既存リポジトリのワークフロー

既存のリポジトリは、開発用ヘルパーのために `privileged`、`SYS_PTRACE`、Docker
socket のマウントを要求することがあります。
この構成では、`/var/run/docker.sock` は互換用シンボリックリンクを介して内部の
rootless socket を指し、外側のデーモンには到達しません。各リポジトリの Compose
ワークフローは、引き続き個別にテストする必要があります。外側のデーモンを本当に
必要とするワークフローは、この境界と互換性がありません。

内部 socket も強力な Docker 管理 API です。これを受け取ったコンテナは、内部デーモンを
操作し、そのデーモンから見えるパス（allowlist に登録したリポジトリを含む）を利用
できます。外側の socket と分離されているからといって、内部 socket が無害になるわけでは
ありません。

### ネットワークアクセス

本プロジェクトは、Docker が別途提供する microVM ベースのサンドボックス製品である
Docker Sandboxes のような、外向き通信を deny-by-default にするネットワーク
ポリシーを提供しません。外部ネットワークへのアクセスは別の信頼上の懸念として
扱い、リポジトリの allowlist によってエージェントが外部サービスへ送信できる
内容まで制限されるとは考えないでください。

## エージェントの状態と認証情報

本リポジトリは Codex や Claude のプロジェクト設定をコミットしません。認証情報
と開発者ごとに変化する状態は、名前付きボリュームに保存されます。ホストの
エージェント用ホームディレクトリや SSH 鍵ファイルを、このコンテナに bind mount
しないでください。

プライベートな Git 依存関係のために、Dev Container の起動または再開前に
`SSH_AUTH_SOCK` を設定すれば、ホストの SSH agent を明示的に転送できます。
`prepare-mounts` は値が絶対 Unix socket であることを検証し、専用の中継サービス
向けの bind mount を生成します。workspace に渡されるのは agent プロトコルで
あり、秘密鍵ファイルではありません。特権付きの `docker` サービスにはこの
socket は渡されません。

SSH agent を転送すると、workspace コンテナ内のすべてのプロセスが、agent に
現在読み込まれている鍵で認証を要求できるようになります。必要最小限のリポジトリ
権限を持つ専用の開発用またはデプロイ用キーを使ってください。本番用、管理者用、
または関係のない個人用キーを含む agent は使わないでください。`SSH_AUTH_SOCK`
が未設定なら agent のマウントは生成されません。設定されている値が不正な場合は、
具体的なエラーを出して起動を拒否します。
